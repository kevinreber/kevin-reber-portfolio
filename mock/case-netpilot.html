Netpilot — an AI agent that triages oncall faster than the oncall engineer.

How I helped build LinkedIn's AI-powered oncall triage agent — 27+ runbooks, 20+ infrastructure tools, and an eval framework that grades the agent against real human ground truth.

The problem

When a network alert fires, the human on call has to do six things at once: load the right runbook, query StateDB for the device's current state, ask Topology for the blast radius, check Prometheus and Kusto for what changed, scan recent JIRA, and decide if this is a real fire or a flap.

That work is mostly procedural. It's also high-stakes — getting the order wrong, or missing one signal, means an outage that could've been three minutes turns into thirty. The question wasn't "can an LLM help here?" — it was "can we trust an LLM here?"

The agent doesn't replace the oncall engineer. It does the first 10 minutes of investigation in 30 seconds, so the engineer starts from "here's what we know" instead of "let me start querying."

The shape of the system

A specialized agent inside LinkedIn's MAE platform (Machine-Assisted Engineering). User queries flow through a Claude Code plugin into the agent service, which loads the relevant runbook, dispatches infrastructure tool calls in parallel, checks an incident pattern memory for fingerprint matches in past incidents, and returns synthesized triage guidance.

The interesting decision — classifier vs LLM-routed tools

The agent has 44+ tools across infrastructure, observability, and ticketing. How do you decide which to call for any given query? The obvious answer is "let the LLM pick." That's also the wrong answer.

LLM picks all tools
Slow, expensive, drifts on edge cases. The model sees too many tool descriptions; recall drops as the surface grows.
Keyword classifier + tool group routing CHOSEN
Deterministic triage-vs-analytics classification (no LLM call). Routes Nvidia IB to UFM, NGBB/DCX/XBR to ThousandEyes, DDoS to Kentik. Switches model accordingly: Sonnet for triage, Opus for analytics.
Per-team agent fleet
Right shape for ownership but wrong shape for users. Engineers don't know which agent to ask.

The classifier is ~30 lines of Python. It runs in microseconds. It saves a Claude call on every query. And it's auditable — when triage goes wrong, we can read the classifier's decision tree, not interpret an LLM's reasoning trace.

The thing that broke

After the agent went live, the failure mode wasn't bad triage. It was context overflow. A complex query would call 5–8 tools, each returning multi-kilobyte JSON. The conversation context would balloon past Claude's window, and the request would fail mid-stream with "prompt too long."

The fix was a ContextOverloadRecoveryMiddleware — when a request crashes, truncate old tool outputs (keep the last 8), strip thinking blocks, retry. Roughly 80% of overflows became invisible to the user. The lesson: tool-heavy agents need a recovery layer, not just a token budget.

middleware/context_recovery.py PYTHON 
# Truncate old tool outputs (keep the last N), strip thinking blocks, retry.
# Prevents ~80% of context overflows from becoming user-visible errors.
async def handle_overflow(messages, error, retry_fn, keep_last=8):
    if not is_context_error(error):
        raise
    # Keep only the last N tool_result blocks; older ones become summaries.
    truncated = prune_tool_history(messages, keep_last=keep_last)
    truncated = strip_thinking_blocks(truncated)
    return await retry_fn(truncated)

Live in production, presented to VP, with a 12-month roadmap. The eval framework was the unlock — paired tickets between the agent and the human oncall engineer give us organic ground truth without synthetic test cases. Every triage the agent handles becomes a graded data point for the next.

What I'd do differently

I'd build the eval framework first, not last. We shipped the agent and then spent weeks figuring out "is it actually good?" Building the graders before the agent would've forced clarity on what "good" means earlier.

I'd also push harder on tool-output schemas before adding more tools. The context overflow problem traces back to inconsistent JSON shapes across the 20-tool surface — once you fix that, the recovery middleware is mostly unnecessary.
