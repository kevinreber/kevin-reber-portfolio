Building the AI tooling every engineer at LinkedIn uses.

How we turned scattered one-off agents into a versioned, ACL-gated, marketplace-distributed platform of reusable AI workflows — and what it takes to ship safely at company scale.

The problem

When AI-assisted engineering started landing inside the company, every team built their own version of the same things. A team would write a "query Jira and summarize" agent. Another would build their own. A third would copy the first one but tweak it for their workflow. Five months in, we had a sprawl of one-off agents that all needed the same things: auth, ACL, observability, versioning, a way to ship.

The platform question wasn't "how do we build more agents?" It was: how do we make the next agent take an afternoon, not a quarter?

A skill I write for my team should be installable by your team without a Slack thread, a copy-paste, or a code review.

The shape of the platform

Eight plugin categories — productivity, development, infrastructure, observability, MAE, migration, specialized, ext — each shipping commands, skills, agents, and MCP servers. Every plugin has standard anatomy: a metadata file (.claude-plugin/plugin.json), a README, ACL coverage (required for CI to pass), and optional capabilities. Versioned with semver, distributed through an internal marketplace, validated by pre-commit hooks.

The interesting decision — where does the version live?

Plugin versioning was the platform decision that mattered most. If the marketplace owns versioning, plugins have to coordinate releases. If the plugin owns versioning, we lose central visibility. We picked the second.

Versions in marketplace.json
Central, discoverable, but every release is a coordinated PR. Slows down plugin teams shipping independently.
Versions in plugin.json + auto-bump CHOSEN
Each plugin owns its semver. .auto-version marker triggers patch bump on merge. Manual for minor/major. Marketplace stays a discovery layer, not a release gate.
Git tags only
Simple but no per-plugin granularity. A single repo with 60+ plugins on monolithic tags is a coordination disaster.

This decision had a non-obvious second-order effect: plugins started evolving at different speeds. The Jira plugin shipped a new release every week; the obscure data-warehouse plugin updated once a quarter. That's the sign of a healthy marketplace — uneven cadence, owned by the people closest to the work.

The thing that broke

Six weeks in, I shipped a PR that should have lived in linkedin-plugins/. It accidentally leaked changes into linkedin-dev-workflow, a different package in the same monorepo. Caught in review, but only barely. Cleaning it up required closing the contaminated PR, hard-reseting locally, and creating a clean replacement (#17068).

The fix wasn't more code — it was a pre-PR scope check baked into the dev loop. A small script that diffs your branch against main, groups changes by plugin, and warns when a single PR touches multiple plugin boundaries. The lesson: monorepos need scope guards as much as they need merge gates.

scripts/scope-check.ts TYPESCRIPT 
// Warns when a PR touches multiple plugin boundaries.
// Hooked into pre-push so contamination is caught before review.
async function checkScope(branch: string) {
  const changed = await diffAgainstMain(branch);
  const plugins = new Set(changed.map(extractPluginRoot));

  if (plugins.size > 1) {
    warn(`PR touches ${plugins.size} plugin boundaries:`);
    plugins.forEach(p => warn(`  - ${p}`));
    prompt("Continue? (y/N)");
  }
}

The skills platform is now the standard surface for shipping AI workflows at LinkedIn. New agents inherit auth, ACL coverage, observability, and marketplace distribution by being a plugin. Specialized agents like Netpilot ship through the platform — their plugin lives at linkedin-plugins/specialized/network-oncall/, installable with one command.

What I'd do differently

I'd build the scope-check tooling from day one. It's the kind of guardrail that costs nothing when there's nothing to guard, and pays for itself the first time someone pushes a PR with leaked changes. I learned that lesson the expensive way.

I'd also document the "is this work platform or specialized?" distinction earlier. The healthiest test: does this upstream into the shared ecosystem, or only benefit one agent? If it's the second, it doesn't belong in the platform — even if it's tempting to put it there.
