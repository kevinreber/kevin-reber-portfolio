Neo-decom — multi-DC decommissioning that doesn't lose the fleet.

How I built the state machine and audit layer that safely retires hardware across multiple datacenters — without taking dependent services down with it.

The problem

Decommissioning a piece of production hardware sounds simple — turn it off, remove it from inventory, done. At fleet scale it isn't. The device drains traffic into peers, dependent services hold cached references, the audit trail has to survive a partial failure, and a botched teardown can take out an entire pod.

The previous system was a Python script with try/except blocks and a Slack notification. It worked for tens of devices a quarter. The new requirement was two orders of magnitude bigger, spanning multiple datacenters, with hard correctness guarantees.

Every state had to be reachable, recoverable, and auditable — even if the orchestrator crashed mid-flight.

The shape of the system

Four states, one rollback path. The interesting property isn't the states themselves — it's that every forward edge has a paired reverse edge, and the orchestrator can replay from any persisted state without double-applying side effects.

The interesting decision

The core question wasn't "how do we orchestrate this?" — there are libraries for that. It was: where does the source of truth for "which state is this device in" actually live?

In-memory orchestrator
Fast, simple — but loses everything on crash. Non-starter for fleet scale.
Kafka log + replay
Durable, but every restart had to re-derive current state by replaying the entire log. O(N) cold starts.
Postgres state table + Kafka log CHOSEN
Postgres is the source of truth (queryable, transactional). Kafka is the audit trail. Restart is O(1); replay only needed for forensics.
Temporal / Cadence
Right shape, wrong dependency. Rejected for ops cost — adding a new clustered service to network infra was a tougher sell than a Postgres table.

The thing that broke

Three months in, a regional outage triggered ~400 simultaneous DRAIN states. The Postgres write throughput was fine. The Kafka producer was fine. The downstream consumer wasn't — it processed events in order, and one bad device was blocking the queue head, holding up the other 399.

The fix was a per-device partition key on the Kafka topic, so a stuck device only blocks its own partition. The lesson: a state machine is only as parallel as its slowest consumer. Now part of the runbook.

orchestrator/transition.rs RUST 
/// Transitions a device to the next state with audit + rollback safety.
/// Returns Err(_) without mutating state if any precondition fails.
pub async fn transition(
    device: &DeviceId,
    target: State,
    tx: &mut Transaction<'_>,
) -> Result<StateChange> {
    let current = State::load(device, tx).await?;

    // Reject illegal transitions before any side effect.
    if !current.can_advance_to(&target) {
        return Err(Error::IllegalTransition { current, target });
    }

    // Single transaction: state row + audit row commit together or not at all.
    State::write(device, target, tx).await?;
    Audit::record(device, current, target, tx).await?;

    Ok(StateChange { device: device.clone(), from: current, to: target })
}

SURVIVED INCIDENTS

Three production incidents that would've been irrecoverable in the previous system were recovered in under an hour because every host's state was a queryable row, not a Slack message. The runbook for "what's stuck and why" is now a SQL query.

What I'd do differently

I'd reach for the per-partition consumer pattern from day one instead of waiting for the incident to teach me. And I'd write the rollback paths before the forward paths — they're harder to get right, and writing them first forces honesty about which state transitions are actually reversible.
